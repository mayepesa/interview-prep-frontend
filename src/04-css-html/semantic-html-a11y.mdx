## ¿Qué es el HTML semántico y por qué importa?

**HTML semántico** significa elegir cada etiqueta por lo que el contenido **es**, no por cómo se ve: un botón es `<button>`, un enlace es `<a href>`, una lista es `<ul>`, el contenido principal es `<main>`. El aspecto se cambia después con CSS.

El navegador convierte el DOM en un **árbol de accesibilidad**: cada nodo tiene un _rol_ (botón, enlace, encabezado), un _nombre accesible_ (el texto que se lee) y un _estado_ (marcado, expandido, deshabilitado). Los lectores de pantalla (VoiceOver, NVDA, JAWS) leen ese árbol, no los píxeles. Con etiquetas semánticas ese árbol se llena solo; con `<div>` queda vacío.

Lo que ganas gratis con HTML semántico:

- **Teclado**: botones, enlaces e inputs reciben foco con Tab y se activan con Enter o Espacio.
- **Lectores de pantalla**: anuncian "botón", "enlace", "encabezado nivel 2", "lista de 5 elementos".
- **SEO**: los buscadores entienden mejor la estructura.
- **Menos código**: no tienes que reimplementar foco, teclado ni roles.

### Landmarks (regiones)

Los _landmarks_ son regiones que el lector de pantalla permite saltar directamente, como un índice de la página:

| Etiqueta                    | Rol implícito   | Uso                                        |
| --------------------------- | --------------- | ------------------------------------------ |
| `<header>` (hijo de `body`) | `banner`        | Logo, navegación global                    |
| `<nav>`                     | `navigation`    | Grupos de enlaces de navegación            |
| `<main>`                    | `main`          | El contenido principal. **Uno por página** |
| `<aside>`                   | `complementary` | Contenido relacionado (sidebar)            |
| `<footer>` (hijo de `body`) | `contentinfo`   | Pie de página                              |
| `<section>` con nombre      | `region`        | Sección con un título propio               |
| `<form>` con nombre         | `form`          | Un formulario                              |

Si hay dos `<nav>`, dales nombre con `aria-label` ("Principal", "Paginación") para distinguirlas.

### Headings (encabezados)

Los encabezados `h1`…`h6` forman el **esquema** de la página. Muchos usuarios de lector de pantalla navegan saltando de encabezado en encabezado. Reglas:

- Un `h1` que describe la página.
- No saltes niveles (de `h2` a `h4`) para conseguir un tamaño: el tamaño se cambia con CSS.
- No uses un encabezado solo porque el texto es grande y negrita.

<Example title="estructura semántica de una página">

```html
<header>
  <a href="/">Timesheets</a>
  <nav aria-label="Principal">
    <ul>
      <li><a href="/week" aria-current="page">Semana</a></li>
      <li><a href="/reports">Reportes</a></li>
    </ul>
  </nav>
</header>

<main>
  <h1>Mis horas</h1>
  <section aria-labelledby="week-title">
    <h2 id="week-title">Semana 42</h2>
    <table>
      …
    </table>
  </section>
</main>

<footer>© 2026</footer>
```

</Example>

<SayIt>
  Semantic HTML means picking elements for what the content is. The browser builds the accessibility
  tree from them, so screen readers get roles, names and states for free, and buttons and links work
  with the keyboard out of the box.
</SayIt>

## ¿Qué diferencia hay entre un `<div onClick>` y un `<button>`?

Visualmente pueden ser idénticos, pero un `<div>` con `onClick`:

- **no recibe foco** con Tab (no está en el orden de tabulación),
- **no se activa** con Enter ni Espacio,
- el lector de pantalla **no anuncia** que es un botón (no tiene rol),
- no se puede deshabilitar con `disabled`.

Para igualar a un `<button>` tendrías que agregar `role="button"`, `tabIndex={0}`, un `onKeyDown` que maneje Enter y Espacio, y estilos de foco. Es más código y más fácil de romper. La regla: **si hace algo, es un `<button>`; si te lleva a otra URL, es un `<a href>`.**

<Example title="prueba los dos solo con el teclado">

<Compare>
<Bad>

```tsx
<div className="btn" onClick={save}>
  Guardar
</div>
```

</Bad>
<Good>

```tsx
<button type="button" onClick={save}>
  Guardar
</button>
```

</Good>
</Compare>

</Example>

<Pitfall>
  Un `<button>` dentro de un `<form>` es `type="submit"` por defecto. Si es un botón de "Cancelar" o abre un
  menú, ponle `type="button"` para que no envíe el formulario.
</Pitfall>

<SayIt>
  A div with onClick looks like a button but isn't one: it can't be focused with Tab, it doesn't
  respond to Enter or Space, and screen readers don't announce it. A native button gives all of that
  for free, so if it performs an action I use a button, and if it navigates I use a link.
</SayIt>

## ¿Cómo haces accesible un formulario con errores?

Un formulario accesible cumple cuatro cosas:

1. **Cada campo tiene un `<label>` conectado.** Con `htmlFor` (en JSX; `for` en HTML) apuntando al `id` del input, o envolviendo el input con el label. El label es el _nombre accesible_ del campo, y además hacer clic en él enfoca el input. Un `placeholder` **no** reemplaza al label: desaparece al escribir y tiene poco contraste.
2. **El error está conectado al campo** con `aria-describedby="id-del-error"`. Así, al enfocar el input, el lector lee el label y después el mensaje de error.
3. **El campo se marca como inválido** con `aria-invalid="true"`, que el lector anuncia como "inválido".
4. **El error se anuncia cuando aparece.** Un elemento con `role="alert"` es una _live region_: el lector lee su contenido en cuanto se inserta, aunque el foco esté en otro lado. Para mensajes no urgentes ("Guardado") se usa `role="status"`, que espera a que el usuario termine lo que está haciendo.

Otros detalles: `autoComplete` correcto (`email`, `name`, `current-password`) para que el navegador autocomplete; el `type` correcto (`email`, `tel`, `number`) para el teclado móvil; y no depender solo del color para marcar un error (agrega texto o un ícono).

<Example title="campo de email con error accesible">

```tsx
const id = useId(); // ids únicos aunque el componente aparezca dos veces

<label htmlFor={`${id}-email`}>Email</label>
<input
  id={`${id}-email`}
  name="email"
  type="email"
  autoComplete="email"
  aria-invalid={error ? true : undefined}
  aria-describedby={error ? `${id}-error` : undefined}
/>
{error && (
  <p id={`${id}-error`} role="alert">
    {error}
  </p>
)}
```

<Live hint="envía vacío; con lector de pantalla se anuncia el error">
  <AccessibleForm />
</Live>

</Example>

<Tip>
  `noValidate` en el `<form>` desactiva los globos de validación del navegador para mostrar los tuyos. Si no
  tienes un diseño propio, la validación nativa (`required`, `type="email"`) ya es bastante accesible.
</Tip>

<SayIt>
  Every input gets a real label connected with htmlFor. When validation fails I set aria-invalid on
  the field, link the error message with aria-describedby, and render the message with role="alert"
  so screen readers announce it immediately.
</SayIt>

## ¿Qué es ARIA y cuándo usarlo?

**ARIA** (Accessible Rich Internet Applications) es un conjunto de atributos que modifican el árbol de accesibilidad: `role`, `aria-label`, `aria-expanded`, `aria-controls`, `aria-live`, etc. **Solo cambia lo que se anuncia**: no agrega foco, ni teclado, ni comportamiento.

Tres tipos de atributos:

- **Roles**: qué es el elemento (`role="tab"`, `role="dialog"`, `role="alert"`).
- **Propiedades**: relaciones y nombres (`aria-label`, `aria-labelledby`, `aria-describedby`, `aria-controls`).
- **Estados**: cosas que cambian (`aria-expanded`, `aria-selected`, `aria-checked`, `aria-invalid`, `aria-busy`).

La **primera regla de ARIA** (del W3C): _si existe un elemento HTML nativo con el rol y el comportamiento que necesitas, úsalo en vez de agregar ARIA._ Por eso se dice que "no ARIA es mejor que mal ARIA": un `role="button"` en un `div` promete un botón que no funciona con teclado.

Cuándo sí usar ARIA:

- **Botones de solo ícono**: `aria-label="Cerrar"`.
- **Estados de componentes propios**: `aria-expanded` en el botón de un acordeón o menú.
- **Widgets que no existen en HTML**: tabs, combobox, tree, siguiendo los patrones de la _WAI-ARIA Authoring Practices Guide_ (APG).
- **Contenido que cambia solo**: `aria-live="polite"` para resultados de búsqueda, notificaciones.

<Example title="ARIA que agrega información que HTML no tiene">

```tsx
// botón de solo ícono: necesita un nombre
<button type="button" aria-label="Cerrar diálogo" onClick={close}>
  <XIcon aria-hidden="true" />
</button>

// acordeón: el estado abierto/cerrado
<button type="button" aria-expanded={open} aria-controls="filters" onClick={toggle}>
  Filtros
</button>
<div id="filters" hidden={!open}>…</div>

// región que se actualiza sola
<p aria-live="polite">{results.length} resultados</p>
```

</Example>

<Pitfall>
  `aria-hidden="true"` oculta un elemento del lector, pero **no** del teclado. Nunca lo pongas en
  algo que puede recibir foco (un botón, un link): el usuario llegaría a un elemento "invisible".
</Pitfall>

<SayIt>
  ARIA changes what assistive technology announces, but it adds no behavior. The first rule of ARIA
  is to use a native element when one exists. I reach for ARIA for icon-only buttons, states like
  aria-expanded, live regions, and custom widgets like tabs, following the WAI-ARIA authoring
  practices.
</SayIt>

## ¿Cómo funciona la navegación con teclado y el foco?

Muchas personas usan solo el teclado (por una discapacidad motora, por preferencia o con un lector de pantalla). Lo mínimo:

- **Todo lo interactivo se alcanza con Tab** y se activa con Enter/Espacio.
- **El orden de Tab sigue el orden visual**, que viene del orden en el DOM. No lo arregles con números en `tabIndex`.
- **El foco siempre es visible.**
- **El foco se gestiona en cambios grandes**: al abrir un modal, el foco entra al modal y queda atrapado dentro (_focus trap_); al cerrarlo, vuelve al botón que lo abrió. `Esc` lo cierra. El elemento nativo `<dialog>` con `showModal()` hace gran parte de esto.

### `tabIndex`

| Valor       | Efecto                                                                           |
| ----------- | -------------------------------------------------------------------------------- |
| `0`         | Entra en el orden normal de Tab (para un elemento propio que debe recibir foco). |
| `-1`        | No entra en el orden de Tab, pero se le puede dar foco con `element.focus()`.    |
| mayor que 0 | Salta al principio del orden. **Evítalo**: rompe el orden lógico.                |

### `:focus` vs `:focus-visible`

`:focus` se aplica siempre que un elemento tiene foco, también al hacer clic con el mouse. `:focus-visible` se aplica solo cuando el navegador cree que el usuario necesita ver el foco (normalmente, al navegar con teclado). Así puedes mostrar un anillo de foco claro sin que aparezca en cada clic. Lo que **nunca** se hace es `outline: none` sin reemplazo.

```css
button:focus-visible {
  outline: 2px solid var(--accent);
  outline-offset: 2px;
}
```

### Roving tabindex

En un grupo de opciones (tabs, toolbar, menú, radio group) Tab no recorre cada opción: **Tab entra al grupo y sale de él**, y las **flechas** se mueven dentro. Se implementa con _roving tabindex_: solo el elemento activo tiene `tabIndex={0}`; los demás tienen `-1`. Al presionar una flecha, mueves el `0` al siguiente y le das foco con `.focus()`.

<Example title="tabs con teclado (patrón WAI-ARIA)">

```tsx
<div role="tablist" aria-label="Vista" onKeyDown={onKeyDown}>
  {TABS.map((tab, i) => (
    <button
      key={tab}
      ref={(el) => { refs.current[i] = el; }}
      role="tab"
      aria-selected={i === active}
      aria-controls="panel"
      tabIndex={i === active ? 0 : -1} // roving tabindex
      onClick={() => setActive(i)}
    >
      {tab}
    </button>
  ))}
</div>
<div role="tabpanel" id="panel" tabIndex={0}>…</div>

// en onKeyDown: ArrowRight/ArrowLeft/Home/End calculan `next`,
// luego setActive(next) y refs.current[next]?.focus()
```

<Live hint="haz Tab hasta una tab, usa las flechas y Home/End, y luego Tab otra vez">
  <KeyboardTabs />
</Live>

</Example>

<SayIt>
  Everything interactive must be reachable with Tab in a logical order and have a visible focus
  style, which I do with :focus-visible. For composite widgets like tabs I use a roving tabindex:
  only the active item is in the tab order and the arrow keys move focus inside the group. For
  modals I trap focus and return it on close.
</SayIt>

## ¿Cómo escribir un buen texto alternativo?

El atributo `alt` de `<img>` es lo que se lee cuando la imagen no se ve (lector de pantalla, imagen rota, conexión lenta).

- **Imagen informativa**: describe lo que aporta en ese contexto, no "imagen de". Para un gráfico, el dato principal: `alt="Horas por semana: subieron de 30 a 38 en octubre"`.
- **Imagen decorativa**: `alt=""` (vacío). El lector la ignora. **No** omitas el atributo: sin `alt`, algunos lectores leen el nombre del archivo.
- **Imagen dentro de un enlace o botón**: el `alt` describe la acción (`alt="Ir al inicio"`), no el dibujo.
- **Íconos SVG**: `aria-hidden="true"` si son decorativos, y el nombre lo da el botón o un `aria-label`.

<Example title="alt según el propósito">

```html
<img src="chart.png" alt="Horas por semana: subieron de 30 a 38 en octubre" />
<img src="divider.svg" alt="" />
<a href="/"><img src="logo.svg" alt="Timesheets, ir al inicio" /></a>
```

</Example>

<SayIt>
  Alt text describes what the image means in context. Decorative images get an empty alt so screen
  readers skip them, and an image inside a link describes where the link goes.
</SayIt>

## ¿Qué es el contraste y cuánto se necesita?

El **contraste** es la diferencia de luminosidad entre el texto y su fondo. Las pautas **WCAG 2.2** (el estándar que exigen la mayoría de las leyes y clientes) piden, en el nivel **AA**:

| Contenido                                     | Contraste mínimo |
| --------------------------------------------- | ---------------- |
| Texto normal                                  | 4.5:1            |
| Texto grande (≥ 24px, o ≥ 18.66px en negrita) | 3:1              |
| Bordes de inputs, íconos, anillo de foco      | 3:1              |

El contraste se calcula con la _luminancia relativa_ de los dos colores: `(L1 + 0.05) / (L2 + 0.05)`, de 1:1 (igual) a 21:1 (negro sobre blanco). Tampoco comuniques algo **solo con color** (un error solo en rojo): las personas con daltonismo no lo distinguen.

<Example title="calculadora de contraste">

```ts
const ratio = (lighter + 0.05) / (darker + 0.05); // luminancias relativas, 0 a 1
const passesAA = ratio >= 4.5; // texto normal
```

  <ContrastChecker />
</Live>

</Example>

<SayIt>
  WCAG AA asks for a contrast ratio of at least 4.5 to 1 for normal text and 3 to 1 for large text
  and UI elements like input borders and focus rings. I also never rely on color alone to convey
  meaning.
</SayIt>

## ¿Cómo compruebas que una pantalla es accesible?

Ninguna herramienta automática detecta todo: se estima que encuentran una parte de los problemas (contraste, labels faltantes, ARIA inválido), pero no si el orden del foco tiene sentido o si un texto alternativo es útil. Lo que funciona es combinar:

1. **Teclado**: desconecta el mouse y usa la pantalla con Tab, Shift+Tab, Enter, Espacio, Esc y flechas. ¿Llegas a todo? ¿Ves siempre el foco? ¿Puedes salir de un modal?
2. **Lighthouse** (en Chrome DevTools): auditoría de accesibilidad con puntaje.
3. **axe DevTools** (extensión) o **axe-core** en los tests (`jest-axe`, `@axe-core/playwright`) para que CI falle si se cuela un problema.
4. **Lector de pantalla**: VoiceOver (macOS, Cmd+F5) o NVDA (Windows) en los flujos principales.
5. **Zoom al 200%** y modo de alto contraste: que nada se corte ni se superponga.
6. **Testing Library**: si puedes encontrar un elemento con `getByRole("button", { name: "Guardar" })`, también lo encuentra un lector de pantalla.

<Example title="accesibilidad en un test de Playwright">

```ts
import AxeBuilder from "@axe-core/playwright";

test("la página de horas no tiene violaciones de accesibilidad", async ({ page }) => {
  await page.goto("/week");
  const results = await new AxeBuilder({ page }).analyze();
  expect(results.violations).toEqual([]);
});
```

</Example>

<SayIt>
  I combine automated and manual checks: Lighthouse or axe catch things like missing labels and low
  contrast, but I also go through the flow with only the keyboard and a screen reader, because tools
  can't tell if the focus order makes sense. In tests, querying by role keeps components accessible.
</SayIt>
